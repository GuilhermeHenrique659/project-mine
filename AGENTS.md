# AGENTS.md

## Project

A Factorio-style game with RTS elements, written in C++20 with raylib.

- `src/` — game code
- `tests/` — tests (GoogleTest)
- `include/`, `lib/` — libraries already bundled in the project: raylib, enet, tmxlite (MinGW)
- `resource/` — assets (outside git)
- `build/` — CMake output (outside git)

## Build

Requires MSYS2 UCRT64 (g++, ninja), CMake and GoogleTest (`pacman -S mingw-w64-ucrt-x86_64-gtest`).

```
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

- Game: `build/project-mine.exe`
- Tests: `build/project-mine-tests.exe`
- Dev run: start the game from the project root; `.env` there (`PROJECT_MINE_DATA_DIR=resource`) is read at startup, so settings are saved in `resource/settings.cfg`. A real environment variable or `--data-dir` overrides it.

The project path contains an accent ("Área de Trabalho") and the MinGW linker does not open absolute paths with accents; that is why `CMakeLists.txt` passes `lib/` as a relative path. Keep it this way when adding libraries.

## Architecture

### Code structure (`src/`)

| Module | Namespace | Role |
|---|---|---|
| `main.cpp` | — | Only creates `Game`, calls `start_up()` and `run()`. Tests exclude it. |
| `game/` | `game` | `Game` owns the window, the main loop, the active scene and the `EventBus`. `game_events.hpp` holds the business events (`NewGameRequested`, `LoadGameRequested`, `CreateGameRequested`, `LoadSaveRequested`, `SaveGameRequested`, `SettingsRequested`, `BackToMenuRequested`, `DisplaySettingsChanged`, `QuitRequested`); `display_settings.hpp` has `DisplaySettings` and the resolution presets; `save_game.hpp` has `SaveGame` (name + creation time + world seed + `entities`, a list of `EntityRecord { archetype, label, fields }`: plain strings, so `game/` and `persistence/` know no ECS types) and `random_seed()` and the save-name rules (`is_valid_save_name()`, `normalize_save_name()`). `Game` applies display settings to the window, switches scenes, and owns the save rules: it creates, loads and writes saves through `persistence::SaveStore` (`Game(data_dir, clock, seed_source)` takes the clock and the seed source so tests get a fixed creation time and seed; a new game draws its world seed from the source). |
| `event/` | `event` | `EventBus` (synchronous, type-safe publish/subscribe), `ScopedSubscription` (RAII unsubscribe) and `subscribe_scoped<E>()`. Header only. |
| `scene/` | `scene` | `Scene` composes a `Model`, a `View` and a `Controller` (MVC). Model and view may be null. `scene/menu/` is the title/main menu scene (`MenuView`, `make_title_scene()`); `scene/settings/` is the settings screen (`SettingsView`, `make_settings_scene()`); `scene/new_game/` asks for the save name (`NewGameView`, `NewGameController`, `make_new_game_scene()`); `scene/load_game/` lists the saves (`LoadGameView`, `make_load_game_scene()`); `scene/world/` is the main in-game scene (`WorldModel`, `WorldView`, `make_world_scene(game, save)`; the game logic is in `core/` and the `Renderer`s in `render/`, see below): `WorldModel(bus, save)` owns the `core::Registry`, spawns the player character, keeps its `world::System`s in a `std::vector<std::unique_ptr<::world::System>>` and runs them in order in `update()` and takes the `input::InputHandler` in its constructor and passes it to `world::PlayerInputSystem`, so movement input never goes through the controller (the controller only handles the pause and menu actions on the same handler, which `make_world_scene` creates and shares); `WorldModel` also holds the pause state (`toggle_pause()`, no simulation while paused); the Pause action (Esc) toggles it and `WorldView` is a host for a list of `scene::world::Renderer`s (`renderer.hpp`: `visible()`, `update()` polls input, `draw(canvas, screen)`), built by `make_world_scene` and injected; they are drawn in list order (first = bottom), updated topmost first, and skipped while not `visible()`. Today: `render/` has the renderers: `TerrainRenderer(terrain)` draws the visible tiles as isometric diamonds below everything: green (grass), blue (water), grey (iron), orange (copper), black (coal); `tile_color(TileType)` gives the colour of a type, and `EntityRenderer(registry)` draws each entity with a `Position` as a `Cube(size)` (`render/cube.hpp`, reusable: front face of `size` pixels, top face above it, `bounds(center)`) with its label and, for characters, the state, and `WorldMenu(bus, model, pointer)` is the pause menu (save name/date, Save, Main Menu): visible only while paused, it reads the mouse itself through an injected `input::Pointer`; `PlayerMenu(model, pointer)` is the player menu (Tab): a panel over 90% of the screen with a `ui::TabBar` (Inventory active, Statistics and Logistics disabled), a red X button in the top-right corner that closes it (`WorldModel::close_player_menu()`), and the Inventory page, an `InventoryGrid(registry, entity)` (rows of 10 button-like slots, `theme::slot_style()`, the one under the mouse in the hover colour; item colour via `item_color()` + count), visible while `WorldModel::is_player_menu_open()` and not paused. `PlayerHud(model, pointer)` is the heads-up display, today only the build bar (B, `WorldModel::toggle_build_bar()`, ignored while paused): a row of icon tabs at the bottom centre, one per `::world::construction_catalog()` category; clicking a tab opens a drop-up list of its constructions (icon + name) above the bar, clicking it again closes it, clicking a construction selects it (`selected()`, not used yet) and closes the list; icons are texture names that are not registered, so the fallback texture is the placeholder. `WorldModel::toggle_player_menu()` is ignored while paused and the simulation keeps running while the menu is open; `cancel()` (Esc) closes the menu first, otherwise toggles the pause. A renderer gets what it depends on (registry, event bus, input) in its constructor, like a model system. `scene::View` has an optional `update()`, called by `Scene::update()` after the model. Inside `scene::`, the top-level `world` and `core` namespaces are written `::world` and `::core` when a name could be ambiguous (`core` has no clash today, `world` does). |
| `ui/` | `ui` | Reusable, raylib-free widget toolkit: `Style` (CSS-like), builders (HTML-like), `Widget` base, `Label`, `Button`, `Input`, `Checkbox`, `Dropdown`, `Card`, `TabBar` (a row of button-like tabs, one active; `theme::tab_style()` / `active_tab_style()` (green) / `disabled_tab_style()`; disabled tabs ignore clicks; `on_change(index)`), `draw_raised()` (paints any area like a button face: fill, outline, bevel), `FocusGroup`/`Focusable` (keyboard navigation), `Canvas` (drawing surface). Only `raylib_canvas.cpp` touches raylib. |
| `input/` | `input` | Keyboard abstraction: `Key`, `Action`, `Keyboard` (interface), `InputMap` (key → action bindings, rebindable; `menu_defaults()` for menus, `text_entry_defaults()` for screens with a text field, which leaves letters and Space unbound) and `InputHandler` (polls the keyboard, runs the handler of each triggered action). `Keyboard::next_char()` returns the characters typed this frame for text fields; `Keyboard::is_down()` is true while a key is held and `InputHandler::is_held(Action)` exposes it per action (continuous input such as walking). `Action` includes `MoveUp/MoveDown/MoveLeft/MoveRight`; `InputMap::world_defaults()` binds WASD to them and arrows/Enter/Space to navigate/confirm, Esc to `Pause`, Tab to `ToggleInventory` and B to `ToggleBuildMenu`. Only `raylib_keyboard.cpp` touches raylib. `Pointer` (`pointer.hpp`) is the mouse counterpart (`position()`, `released()` for a left click, `scroll()` for the wheel: the world controller zooms the camera with it, limited by `Camera::MinZoom`/`MaxZoom`), implemented by `raylib_pointer.cpp` and faked in tests; the world screen injects it into its renderers, while the other screens still read the mouse in their controllers. |
| `persistence/` | `persistence` | Saves user data to disk. `SettingsStore` reads/writes `settings.cfg` (`key=value`, written via a temp file + rename); `SettingsPersistence` subscribes to `DisplaySettingsChanged` on the `EventBus` and saves; `resolve_data_dir()` picks the data directory: `--data-dir <path>` > env `PROJECT_MINE_DATA_DIR` > build default (Debug: `resource/` relative to the working dir, Release: `%APPDATA%/ProjectMine`). `Game(data_dir)` loads the saved settings at startup and opens the window with them. `SaveStore` (saves `name`, `created_at`, `seed` and the entities; format version 2 writes each record as an `[entity]` section of `archetype=`, `label=` and `key=value` fields after the header; a record without archetype is dropped, field keys `archetype`/`label` and keys/values with line breaks are not written, a file with a newer `version` is not loaded (so saving cannot drop its unknown data), a v1 file or a save without a seed loads with no entities / seed 0) reads/writes saved games as `saves/<name>.sav` (`key=value`): every save first moves the existing file to `<name>.sav_old` (replacing the previous backup), `load()` falls back to that backup when the current file is missing or corrupt, and `list()` returns the loadable saves newest first. `write_file_atomically()` (`atomic_file.hpp`) is the shared temp file + rename (+ optional backup) write. Raylib-free. |
| `core/` | `core` | Generic ECS, header only, raylib-free. `entity.hpp`: `EntityId` and `Entity { id, label }`. `registry.hpp`: `Registry` creates/destroys entities (ids sequential, never reused), attaches components (`add<C>`, `get<C>`, `has<C>`, `remove<C>`) and runs systems over them with `each<Cs...>(fn)`. |
| `scene/world/core/` | `world` | Game logic of the world (the ECS content: components, systems, entities, events, isometric math), built on the generic `core/`. It lives under `scene/world/` but is raylib-free and view-free: it never includes `ui/`, raylib or anything else of `scene/` (not `render/`, `WorldModel`, `WorldView`); it may use `input/` actions, injected as an `input::InputHandler`. Subfolders add no namespace, and the folder name is not the namespace (`world::`; do not confuse it with the generic `core::`). `components/` has `Character` (marks a character and holds its `CharacterState`: `Idle` or `Moving`), `Position` (a `WorldPoint`) and `Mover` (speed in tiles/s + direction intent) and `Inventory` (`inventory.hpp` + `.cpp`: a fixed number of slots, each one `ItemStack`; `add()` returns what did not fit and tops up same-type stacks before using empty slots, `remove()` returns what it took, from the last slots first, `count()`, `free_slots()`; attachable to any entity, not used by the player or saved yet); `items/item.hpp` has `ItemType` (`IronOre`, `CopperOre`, `Coal`), `Item { type, max_stack }` (definitions in `items::`, 100 each), `ItemStack { item, count }` and `to_string(ItemType)`; `system.hpp` has the `System` base class (`update(dt)`; a system gets the registry and bus in its constructor) and `systems/player_input_system.hpp` has `PlayerInputSystem(registry, input)`, which sets the `Mover` direction of `PlayerControlled` entities from the held `Move*` actions (screen space turned into world space); it is registered before `CharacterMoveSystem` because order in the list is order of execution; `systems/character_move_system.hpp` has `CharacterMoveSystem(registry, bus)`, whose `update(dt)` moves only entities with `Character` + `Position` + `Mover` (normalizes the direction so diagonals are not faster), sets the state and publishes `CharacterStateChanged{entity}` (`events/character_state_changed.hpp`) on the `EventBus` only when a character starts or stops moving; `terrain/terrain.hpp` has `Terrain(seed)`, a flat unbounded world of `TileType::Grass` / `Water` / `IronOre` / `CopperOre` / `Coal` (`is_ore()`) where `tile_at(tile)` is a pure function of the seed (value noise; the `SpawnClearRadius` around (0,0) is always grass; three medium starting ore nodes, one per type, sit 24–36 tiles out, each on the first dry spot found around its seed-random angle (when no spot is fully dry, the driest one is used and its footprint is turned into land), so ore never touches water; scattered nodes live one per 64-tile cell, only on land, none inside `StartingAreaRadius` (64), with a radius that grows with the distance from (0,0) up to a cap; node edges are irregular via the noise), so a loaded save recreates the same world; `WorldModel` builds it from `save.seed` (`terrain()`); `construction/construction.hpp` has `ConstructionCategory` (`Special`, `Mine`, `Factory`, `Military`), `Construction { name, icon }`, `ConstructionGroup` and `construction_catalog()` (the buildable constructions by category, in build bar order; nothing builds them yet); `entities/character.hpp` has `spawn_character()` (an archetype: `Character` + `Position` + `Mover` at `CharacterSpeed` + an `Inventory` of `CharacterInventorySlots` (40)). Persistence of entities: `components/persistent.hpp` has `Persistent{archetype}` (only entities with it are saved); `entities/entity_factory.hpp` has `EntityFactory` (archetype name → spawn function, injected, `make_entity_factory()` registers `"character"`; `spawn()` adds `Persistent`; `WorldModel` spawns the new-game player through it too); `save/component_codec.hpp` has `ComponentCodec` (`write` / `read` of one component's `Fields`) with `PositionCodec`, `CharacterCodec` (writes and restores `Moving`/`Running` as `Idle` through `saved_state()`) and `PlayerControlledCodec` and `InventoryCodec` (`inventory.<slot>=<ItemType>:<count>` per filled slot, invalid entries skipped) in `save/codecs.hpp`; `save/world_serializer.hpp` has `WorldSerializer` (`snapshot()` / `restore()`, `make_world_serializer(factory)` lists the codecs: a new saved component = one codec there). Entity ids are not saved. This is the one place where `world::` depends on `game/save_game.hpp` (plain data). `WorldModel` restores the entities in its constructor (spawning the default player when the save has none or no player), centres the camera on the player, and `save_game()` returns the header plus a fresh snapshot (`save_header()` is the header alone, without the snapshot; `WorldModel` is not copyable or movable, as the serializer and systems refer to its members); `WorldMenu` calls it when Save is clicked, so the saved position is the one at click time. `camera.hpp` has `Camera` (`center`, `projection(w, h)` puts the centre at the middle of the screen); `WorldModel` owns it (`camera()`) and `systems/camera_follow_system.hpp` has `CameraFollowSystem(registry, camera)`, registered after `CharacterMoveSystem`, which centres it on the `PlayerControlled` entity; `TerrainRenderer` and `EntityRenderer` take the camera and draw through its projection. Isometric world math (2:1 diamond projection) is in `isometric.hpp`, with `screen_direction_to_world()` turning a screen direction into a world one (screen up = world (-1,-1)). `isometric.hpp` has `TileCoord`, `WorldPoint` (continuous, in tiles), `ScreenPoint` and `IsoProjection` (tile size + `origin`, the screen position of world (0,0): move it to scroll, scale the tile size to zoom) with `world_to_screen()`, `screen_to_world()`, `tile_at()` (mouse picking), `tile_center()` and `tile_corners()`; `tile_containing()` floors a world position to its tile; `depth_of()` / `draws_before()` give the back-to-front draw order. |
| `graphics/` | `graphics` | `TextureManager`, a singleton (`TextureManager::instance()`): `Game::start_up()` registers each texture as name → file (`register_texture()`) and installs the loader (`set_loader()`); views and renderers ask for it by name with `get(name)`, which loads it on first use and, when the name is not registered or the file cannot be read, returns the **fallback texture** (a generated magenta/black checkerboard, no file needed; created once through `TextureLoader::create_placeholder()`, null only when there is no loader). `find(name)` is the same lookup without the fallback (null when missing), `fallback()` gives the generic texture itself. `EntityRenderer` does not use textures yet: it draws each entity as a `Cube`. Textures are drawn with `ui::Canvas::draw_texture(texture, dest, TextureDraw{source, tint, flip_x, flip_y, rotation})` (the 2-argument overload draws the whole texture as it is). On top of it: `Sprite` (`sprite.hpp`: texture name + optional source region, whole texture if none) with `draw_sprite(canvas, sprite, dest, options)`, which looks the texture up in the manager, draws the whole fallback instead of a missing texture's region, and returns false (drawing nothing) only when there is no fallback either; `SpriteSheet` (`frame(i)` / `frames(first, count)`, grid numbered left to right, top to bottom) and `Animation` (`sprite_at(elapsed_seconds)`, fixed fps, loop or hold the last frame; it keeps no clock, the owner accumulates the time). `TextureLoader` is the interface; only `raylib_texture_loader.cpp` touches raylib. Tests install a fake loader and call `reset()` in set-up/tear-down. |
| `logging/` | `logging` | `logging::info()` / `logging::warning()` write to stderr (`[INFO]` / `[WARN]`); `set_sink()` redirects messages (tests capture them). Used by `persistence/` for settings and save-game load/save. Raylib-free. |
| `text/` | `text` | Header only, raylib-free, usable from any module (including `world::`). `parse.hpp`: `text::parse<T>(text)` reads the whole text as an integer or floating-point `T` (empty when there is anything else, a '+', spaces, or the number does not fit; unsigned rejects '-'; locale-independent), and `text::format(value)` writes the shortest text that `parse<T>()` reads back exactly. Use them for every number read from or written to a file instead of hand-written loops or `std::sto*`. |

`tests/` mirrors the `src/` modules (`tests/ui/`, `tests/persistence/`, `tests/scene/menu/`, ...); shared helpers live in `tests/support/` and are included as `"support/..."`: `fake_canvas.hpp` is a recording `Canvas` for widget tests, `fake_keyboard.hpp` a `Keyboard` whose pressed keys, held keys and typed characters the test sets, `fake_pointer.hpp` a `Pointer` whose position and release the test sets, `fake_input.hpp` a world-bindings `InputHandler` over a `FakeKeyboard` for the world model and its systems, `temp_dir.hpp` a temporary directory for persistence tests.

### How the components communicate

```
raylib keyboard ──► input::Keyboard ──► InputHandler ──(Action handlers)──► Controller
raylib mouse ────────────────────────────────────────────────────────────► Controller
                                                                              │
                     Controller: view.handle_pointer(), focus_group().focus_next()/activate_focused()
                                                                              ▼
                      ui widgets (Button, ...)  ──on_click/on_hover/on_leave──► MenuView
                                                                              │ publishes business event
                                                                              ▼
                                       game::Game::event_bus()  (EventBus, owned by Game)
                                                                              │
                                  subscribers react (Game quits on QuitRequested, opens the
                                  New Game / Load Game screens, creates, loads and saves games)
```

- **Layers do not call each other for business rules; they publish events.** A view/widget only announces what the player asked for (`bus.publish(game::QuitRequested{})`). The owner of the rule subscribes and reacts. Do not put game rules in buttons or views.
- **The `EventBus` lives in `Game`** (`game.event_bus()`), is shared by every scene, and is declared first in `Game` so it outlives scenes. Subscribers that can be destroyed before the bus must hold a `ScopedSubscription` (never a bare `subscribe` id).
- **Input is mapped in two steps.** Raw keys → `Action` through `InputMap`/`InputHandler`; the controller registers a handler per `Action` and never names a physical key. On most screens the mouse is read directly by the controller and forwarded with `view.handle_pointer(position, released)`; on the world screen the interactive renderer reads it itself through an injected `input::Pointer` in `View::update()`.
- **UI events live on the widget.** Every widget accepts `on_click`, `on_hover` and `on_leave` (builder methods or `set_on_*`). `Card` forwards pointer events to its children. A disabled `Button` ignores clicks.
- **Popups.** A widget with a popup (`Dropdown`) draws it in `draw_overlay()` (the parent draws overlays after all siblings) and returns `blocks_pointer()` while open, so `Card` sends it all pointer events and clicks never reach widgets underneath.
- **Save flow.** New Game → `NewGameRequested` → name prompt → `CreateGameRequested{name}` → `Game` writes the save and enters the world scene. Load Game → `LoadGameRequested` → save list → `LoadSaveRequested{name}` → `Game` reads the save and enters the world scene (stays on the list if it cannot be read). In the world scene the Save button publishes `SaveGameRequested{save}` with the model's state and `Game` writes it.
- **Text entry.** A screen with a `ui::Input` uses `InputMap::text_entry_defaults()` and its controller forwards `Keyboard::next_char()` to the view each frame; `Action::Erase` (Backspace) erases and confirming the focused field calls its `on_submit`.
- **Keyboard focus** is a `ui::FocusGroup`: add `Focusable` widgets (`Button`, `Input`, `Checkbox`, `Dropdown`), call `focus_next()/focus_previous()/activate_focused()`, and call `focus(widget)` on hover to sync mouse and keyboard (`ui::join_focus_group()` wires both for any control; `ButtonFactory` does it for buttons).
- **Layout and drawing are separate from raylib.** Widgets measure and draw through `ui::Canvas`; `layout()` runs before `draw()` and hit-testing uses the bounds of the last layout.
- **Scene lifecycle.** `Game::change_scene()` applies at the start of the next `update()`. Per frame: `Scene::update()` runs `Controller::handle_input()`, `Model::update()` then `View::update()`; `Scene::draw()` runs `View::draw()`.

### Adding a screen

1. Build the widget tree in a `View` with the `ui::` builders (`ui::card().child(...)`, `ui::button("...").on_click(...)`); publish business events from the click handlers.
2. Add a `Controller` that turns input into calls on the view through an `input::InputHandler` (register one handler per `input::Action`).
3. Put the rules in a `Model` or in an event subscriber, and test them without a window (fake `Keyboard`, `FakeCanvas`, a real `EventBus`).
4. Compose them in a `make_<name>_scene(game::Game&)` factory returning a `scene::Scene`.

## Tests

- **Given / When / Then structure**: every test is organized into three blocks, in this order — *Given* (initial state), *When* (tested action), *Then* (checks).

  ```cpp
  TEST(Inventario, AdicionarItemAumentaQuantidade) {
      // Given
      Inventario inventario;

      // When
      inventario.adicionar(Item::PlacaDeFerro, 3);

      // Then
      EXPECT_EQ(inventario.quantidade(Item::PlacaDeFerro), 3);
  }
  ```

- **Only meaningful tests**: each test must verify a real game behavior (rule, calculation, state transition, edge case). Do not create trivial tests or tests written just to increase coverage (getters/setters, constructors, library code).

## Coding standards

- **Smart pointers are mandatory**: all dynamic memory ownership uses `std::unique_ptr` (default) or `std::shared_ptr` (only when ownership is truly shared). Do not use `new`/`delete` or raw pointers as owners; create objects with `std::make_unique`/`std::make_shared`.
- **Early return whenever possible**: handle invalid and exit cases at the start of the function and return early, instead of nesting `if`/`else`.
- **Naming conventions** (common modern C++ community style):

  | Element | Style | Example |
  |---|---|---|
  | Types (classes, structs, enums, aliases, concepts) | `PascalCase` | `ConveyorBelt`, `ItemStack` |
  | Functions and methods | `snake_case` | `add_item()`, `update_power()` |
  | Variables and parameters | `snake_case` | `tile_size`, `current_tick` |
  | Private/protected data members | `snake_case` + trailing `_` | `items_`, `health_` |
  | Public struct fields | `snake_case` (no suffix) | `position`, `speed` |
  | Constants (`constexpr`/`const` globals) and enumerators | `PascalCase` | `MaxStackSize`, `Item::IronPlate` |
  | Macros | `UPPER_SNAKE_CASE` (avoid when possible) | `PROJECT_MINE_DEBUG` |
  | Namespaces | `snake_case`, short | `world`, `net` |
  | Template parameters | `PascalCase` | `T`, `Allocator` |
  | Files | `snake_case`, `.hpp` / `.cpp` | `conveyor_belt.hpp` |

  Use `enum class` instead of plain `enum`. Test names (GoogleTest suite and case) use `PascalCase`, as in the example above.
